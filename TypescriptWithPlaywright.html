1. What is TypeScript & Why Should an SDET Care?

▼

📖 Theory

TypeScript (TS) is a strongly typed superset of JavaScript developed by Microsoft. It compiles down to plain JavaScript, meaning it runs anywhere JavaScript runs — browsers, Node.js, CI/CD pipelines. TypeScript adds static type checking at compile time, catching bugs before execution.

For an SDET coming from Java, TypeScript feels familiar because:

  • It has types (like Java's int, String, List<T>)
  • It supports Interfaces, Classes, Generics, and Enums
  • It provides access modifiers (public, private, protected)
  • It enables OOP patterns you already know
💡 SDET Tip: TypeScript + Playwright is the modern replacement for Java + Selenium. You get type safety, better IDE autocompletion, and fewer runtime errors in your test suites.

☕ Java vs 🔷 TypeScript — First Glance

Java (Selenium-style)
public class LoginTest {
    private WebDriver driver;
    private String baseUrl = "https://example.com";

    public LoginTest(WebDriver driver) {
        this.driver = driver;
    }

    public void login(String username, String password) {
        driver.findElement(By.id("user")).sendKeys(username);
        driver.findElement(By.id("pass")).sendKeys(password);
    }
}
TypeScript (Playwright-style)
class LoginPage {
    private baseUrl: string = 'https://example.com';

    constructor(private page: Page) {}  // shorthand!

    async login(username: string, password: string): Promise<void> {
        await this.page.fill('#user', username);
        await this.page.fill('#pass', password);
    }
}

Notice the similarities: classes, constructors, type annotations. The async/await pattern in TS mirrors Java's CompletableFuture but is simpler.

2. Setting Up TypeScript + Playwright (SDET Environment)

▼

📖 Theory: The TypeScript Compiler

TypeScript code (.ts files) is compiled to JavaScript (.js) using the tsc compiler. The configuration lives in tsconfig.json. You never ship .ts directly — the browser/Node runs the compiled JS.

Terminal — Project Setup
# 1. Initialize a Node.js project
npm init -y

# 2. Install TypeScript globally (optional) and locally
npm i -D typescript @types/node

# 3. Install Playwright for testing
npm i -D @playwright/test
npx playwright install

# 4. Generate tsconfig.json
npx tsc --init

📄 tsconfig.json — Key Settings for SDETs

tsconfig.json
{
    "compilerOptions": {
        "target": "ES2022",           // Compile to modern JS
        "module": "commonjs",        // Node.js module system
        "strict": true,              // Enable ALL strict checks (recommended!)
        "esModuleInterop": true,
        "outDir": "./dist",          // Compiled JS output folder
        "rootDir": "./src",         // TS source folder
        "sourceMap": true,          // Debug TS directly in browser/IDE
        "forceConsistentCasingInFileNames": true
    },
    "include": ["src/**/*.ts"],
    "exclude": ["node_modules", "dist"]
}
⚠️ Important: Always enable "strict": true. It enables strictNullChecks, noImplicitAny, and other safeguards that prevent entire classes of bugs.

3. Basic Types & Type Annotations

▼

📖 Theory

TypeScript's type system is structural (unlike Java's nominal typing). Types are annotated using : type syntax. TypeScript can also infer types automatically, so you don't always need explicit annotations.

All Primitive Types

TypeScript — Basic Types
// ── Primitives ──
let isPassed: boolean = true;           // Java: boolean
let retryCount: number = 3;             // Java: int / double (TS unifies them)
let testName: string = 'Login Flow';    // Java: String
let bigId: bigint = 9007199254740991n; // Java: long
let uniqueKey: symbol = Symbol('id');  // Java: (no direct equivalent)

// ── Special Types ──
let notSure: unknown = 4;             // Safer than 'any' — requires type checking
let anything: any = 'could be anything'; // Opts out of type checking (avoid!)
let noValue: void = undefined;       // Java: void (for function returns)
let notFound: null = null;
let notSet: undefined = undefined;
let crash: never;                    // Function that never returns (throws error)

// ── Arrays ──
let testTags: string[] = ['smoke', 'regression'];     // Java: List<String>
let scores: Array<number> = [95, 87, 91];       // Generic syntax

// ── Tuple (fixed-length array) ──
let testResult: [string, boolean, number] = ['Login', true, 2.5];

// ── Object literal type ──
let config: { baseUrl: string; timeout: number } = {
    baseUrl: 'https://api.example.com',
    timeout: 30000
};

Type Inference

TypeScript infers types when you initialize a variable. You don't need to annotate everything.

Type Inference Example
let username = 'testuser';   // TS infers: string
// username = 42;          // ❌ Error: Type 'number' is not assignable to 'string'

let response;               // TS infers: any (no initialization = no inference)
response = 200;             // ✅ allowed because it's 'any'

4. Interfaces — Contracts for Your Test Data

▼

📖 Theory

An interface defines a contract — the shape an object must have. Unlike Java, TypeScript interfaces are purely structural (any object with matching properties satisfies the interface). Interfaces can extend other interfaces, have optional properties, readonly properties, and even describe function signatures.

Interfaces for API Testing
// ── Define an interface for API response ──
interface User {
    readonly id: number;            // Cannot be modified after creation
    name: string;
    email: string;
    role?: string;               // Optional property
}

// ── Extending interfaces ──
interface AdminUser extends User {
    permissions: string[];
    accessLevel: number;
}

// ── Interface for a function signature ──
interface ApiValidator {
    (response: Response): boolean;    // Callable signature
}

// ── Usage in a test ──
const user: User = {
    id: 101,
    name: 'John Doe',
    email: 'john@test.com'
    // role is optional, so it's fine to omit
};

// user.id = 202;  // ❌ Error: Cannot assign to 'id' because it's readonly
💡 SDET Tip: Use interfaces to model your API request/response payloads. This gives you autocomplete when writing test assertions and catches mismatched fields at compile time.

5. Classes & Access Modifiers — OOP for Test Frameworks

▼

📖 Theory

TypeScript classes are very similar to Java classes but with some syntactic sugar. You get public, private, protected modifiers, readonly properties, abstract classes, and parameter property shorthand (defining & assigning in the constructor in one line).

Page Object Model with TypeScript
abstract class BasePage {
    protected readonly url: string;

    constructor(protected page: Page, url: string) {
        this.url = url;
    }

    async navigate(): Promise<void> {
        await this.page.goto(this.url);
    }

    abstract isLoaded(): Promise<boolean>;  // Must be implemented by subclasses!
}

class LoginPage extends BasePage {
    // Parameter property shorthand: 'private' auto-assigns
    constructor(
        page: Page,
        private usernameSelector = '#username',
        private passwordSelector = '#password'
    ) {
        super(page, 'https://example.com/login');
    }

    async isLoaded(): Promise<boolean> {
        return await this.page.isVisible(this.usernameSelector);
    }

    async login(user: string, pass: string): Promise<void> {
        await this.page.fill(this.usernameSelector, user);
        await this.page.fill(this.passwordSelector, pass);
        await this.page.click('button[type="submit"]');
    }
}

Compare this to a typical Selenium POM in Java — it's cleaner, more concise, and the async/await pattern eliminates callback hell.

6. Functions — Typed Signatures, Overloads & Async

▼

📖 Theory

TypeScript allows you to type parameters and return values. You can also define optional parameters (?), default values, rest parameters (...args), and function overloads.

Function Types & Overloads
// ── Basic typed function ──
function assertStatus(actual: number, expected: number): boolean {
    return actual === expected;
}

// ── Optional & default parameters ──
function retry(fn: () => Promise<void>, maxAttempts: number = 3, delayMs?: number): Promise<void> {
    for (let i = 0; i < maxAttempts; i++) {
        try { await fn(); return; } catch {}
        if (delayMs) await new Promise(r => setTimeout(r, delayMs));
    }
    throw new Error(`Failed after ${maxAttempts} attempts`);
}

// ── Rest parameters (varargs) ──
function logResults(suiteName: string, ...results: boolean[]): void {
    const passed = results.filter(r => r).length;
    console.log(`${suiteName}: ${passed}/${results.length} passed`);
}
logResults('Smoke', true, true, false, true); // "Smoke: 3/4 passed"

// ── Arrow functions with types ──
const multiply = (a: number, b: number): number => a * b;

// ── Function overloads ──
function parseResponse(body: string): object;
function parseResponse(body: Buffer): object;
function parseResponse(body: string | Buffer): object {
    const raw = typeof body === 'string' ? body : body.toString();
    return JSON.parse(raw);
}

7. Generics — Reusable, Type-Safe Code

▼

📖 Theory

Generics in TypeScript work similarly to Java generics (List<T>, Map<K,V>). They allow you to write type-safe reusable components without sacrificing type information. You can constrain generics with extends.

Generics in Test Utilities
// ── Generic API response wrapper ──
interface ApiResponse<T> {
    status: number;
    data: T;
    message: string;
}

// ── Generic function to fetch and parse ──
async function fetchData<T>(url: string): Promise<ApiResponse<T>> {
    const res = await fetch(url);
    return await res.json() as ApiResponse<T>;
}

// ── Usage with specific types ──
interface User { id: number; name: string; }
const userResp = await fetchData<User>('/api/users/1');
// userResp.data is now typed as User — full autocomplete! ✅

// ── Generic constraint ──
function getProperty<T, K extends keyof T>(obj: T, key: K): T[K] {
    return obj[key];
}
getProperty(userResp.data, 'name'); // ✅ OK
// getProperty(userResp.data, 'nonexistent'); // ❌ Compile error!

8. Enums — Named Constants for Readable Tests

▼

📖 Theory

TypeScript supports both numeric and string enums. String enums are preferred for test automation because they serialize to readable values (great for reporting & logging). You can also use const enum for zero-overhead compile-time inlining (like Java's enum but without the runtime cost).

Enums for Test Status & Browser Types
// ── String enum (preferred for tests) ──
enum TestStatus {
    PASSED = 'PASSED',
    FAILED = 'FAILED',
    SKIPPED = 'SKIPPED',
    FLAKY = 'FLAKY'
}

function reportResult(test: string, status: TestStatus): void {
    console.log(`[${status}] ${test}`);
}
reportResult('Login Flow', TestStatus.PASSED);
// Output: [PASSED] Login Flow

// ── Numeric enum ──
enum HttpStatus {
    OK = 200,
    CREATED = 201,
    NOT_FOUND = 404,
    SERVER_ERROR = 500
}

// ── Const enum (zero runtime cost — inlined at compile time) ──
const enum Browser {
    CHROMIUM = 'chromium',
    FIREFOX = 'firefox',
    WEBKIT = 'webkit'
}

9. Advanced Types — Union, Intersection, Type Guards & Utility Types

▼

📖 Theory

TypeScript offers powerful type operators that have no direct Java equivalent. These are essential for writing flexible yet type-safe test code.

Union Types (|) — "Either this OR that"

Union Types
// A variable that can hold multiple types
type LocatorStrategy = string | RegExp | (() => string);

function findElement(strategy: LocatorStrategy): void {
    if (typeof strategy === 'string') {
        console.log('Using CSS selector:', strategy);
    } else if (strategy instanceof RegExp) {
        console.log('Using regex pattern:', strategy);
    } else {
        console.log('Using dynamic function');
    }
}

Intersection Types (&) — "Combine multiple types"

Intersection Types
interface Timestamped { createdAt: Date; updatedAt: Date; }
interface SoftDeletable { isDeleted: boolean; }

// Combine both into one type
type Entity = Timestamped & SoftDeletable;

const testRecord: Entity = {
    createdAt: new Date(),
    updatedAt: new Date(),
    isDeleted: false
};

Utility Types (Built-in)

Utility TypeDescriptionJava Analogy
Partial<T>All properties optionalBuilder pattern
Required<T>All properties required@NotNull on all fields
Readonly<T>All properties readonlyImmutable objects
Pick<T, K>Select specific keysDTO projection
Omit<T, K>Exclude specific keys—
Record<K, V>Map of keys to a value typeMap<K,V>
ReturnType<F>Extract return type of functionReflection
Utility Types in Action
interface TestConfig {
    baseUrl: string;
    timeout: number;
    retries: number;
}

// For a config override, all fields are optional
type ConfigOverride = Partial<TestConfig>;

const override: ConfigOverride = { timeout: 60000 }; // ✅ Only timeout specified

// Pick only what you need for a report
type ConfigSummary = Pick<TestConfig, 'baseUrl' | 'timeout'>;

Type Guards — Narrowing at Runtime

Type Guards
interface ApiError { status: number; message: string; }
interface ApiSuccess<T> { status: number; data: T; }

type ApiResult<T> = ApiSuccess<T> | ApiError;

// Custom type guard
function isApiError<T>(result: ApiResult<T>): result is ApiError {
    return 'message' in result && !('data' in result);
}

function handleResult<T>(result: ApiResult<T>): void {
    if (isApiError(result)) {
        console.error(`Error: ${result.message}`); // TS knows it's ApiError
    } else {
        console.log('Data:', result.data); // TS knows it's ApiSuccess
    }
}

10. TypeScript vs JavaScript — Complete Comparison

▼

📖 Theory: Key Differences at a Glance

JavaScript is dynamically typed — types are checked at runtime. TypeScript is statically typed — types are checked at compile time. This single difference impacts every aspect of development and testing.

FeatureJavaScript JSTypeScript TS
Type System Dynamic (runtime) Static (compile-time)
Type Annotations ❌ Not available ✅ Full support
Interfaces ❌ No ✅ Yes
Generics ❌ No ✅ Yes
Enums ❌ No (use constants) ✅ Numeric + String enums
Access Modifiers ❌ #private only (ES2022) ✅ public/private/protected
Abstract Classes ❌ No ✅ Yes
Function Overloads ❌ No ✅ Yes
Compilation Step None (runs directly) Requires tsc compilation
IDE Autocomplete Limited Excellent (IntelliSense)
Refactoring Safety Risky (runtime errors) Safe (compile-time errors)
Null Safety No built-in checks strictNullChecks
Learning Curve Lower Slightly higher (worth it!)
Runtime Performance Same Same (compiles to JS)
⚠️ Key Insight: TypeScript's type checking happens only at compile time. At runtime, it's just JavaScript. This means you still need proper error handling and validation in your test code — types won't catch API schema changes at runtime!

Side-by-Side Code Comparison

JavaScript — No type safety
// JS: No types — easy to make mistakes
function calculateCoverage(passed, total) {
    return (passed / total) * 100;
}
calculateCoverage('90', 100);   // 😱 '9010' — string concatenation!
calculateCoverage(90);            // 😱 NaN — missing parameter, no error!
TypeScript — Compile-time safety
// TS: Types catch errors before execution
function calculateCoverage(passed: number, total: number): number {
    return (passed / total) * 100;
}
// calculateCoverage('90', 100);  // ❌ Compile error: string not assignable to number
// calculateCoverage(90);          // ❌ Compile error: expected 2 arguments
calculateCoverage(90, 100);    // ✅ 90 — correct!

11. SDET Practical: Playwright with TypeScript (Real-World Examples)

▼

📖 Theory: Why Playwright + TypeScript?

Playwright was built for TypeScript. Its API is fully typed, meaning you get autocomplete for all locators, assertions, and browser actions. Combined with TypeScript's type safety, your test suite becomes significantly more robust.

Complete E2E Test Example

Playwright Test — Login + API validation
import { test, expect, Page, APIResponse } from '@playwright/test';

// ── Interfaces for type safety ──
interface LoginPayload {
    username: string;
    password: string;
}

interface LoginResponse {
    token: string;
    user: { id: number; name: string; role: string };
}

// ── Page Object with full typing ──
class LoginPage {
    readonly usernameInput = this.page.locator('[data-testid="username"]');
    readonly passwordInput = this.page.locator('[data-testid="password"]');
    readonly submitBtn = this.page.locator('button[type="submit"]');
    readonly errorMsg = this.page.locator('.error-message');

    constructor(private readonly page: Page) {}

    async goto(): Promise<void> {
        await this.page.goto('/login');
    }

    async login(payload: LoginPayload): Promise<void> {
        await this.usernameInput.fill(payload.username);
        await this.passwordInput.fill(payload.password);
        await this.submitBtn.click();
    }
}

// ── API helper (like Rest Assured but typed!) ──
async function apiLogin(request: APIRequestContext, payload: LoginPayload): Promise<LoginResponse> {
    const response = await request.post('/api/auth/login', { data: payload });
    return await response.json() as LoginResponse;
}

// ── The actual test ──
test.describe('Authentication', () => {
    test('should login successfully with valid credentials', async ({ page, request }) => {
        const loginPage = new LoginPage(page);

        await loginPage.goto();
        await loginPage.login({
            username: 'testuser@example.com',
            password: 'SecurePass123!'
        });

        // Assert UI
        await expect(page).toHaveURL(/dashboard/);
        await expect(page.locator('.welcome-banner')).toBeVisible();

        // Validate via API (like Rest Assured!)
        const apiResponse = await apiLogin(request, {
            username: 'testuser@example.com',
            password: 'SecurePass123!'
        });
        expect(apiResponse.token).toBeDefined();
        expect(apiResponse.user.role).toBe('admin');
    });

    test('should show error for invalid password', async ({ page }) => {
        const loginPage = new LoginPage(page);
        await loginPage.goto();
        await loginPage.login({
            username: 'testuser@example.com',
            password: 'WrongPass'
        });
        await expect(loginPage.errorMsg).toContainText('Invalid credentials');
    });
});

API Testing with TypeScript (Rest Assured Replacement)

API Test — Typed Request & Response
import { test, expect } from '@playwright/test';

interface CreateUserRequest {
    name: string;
    email: string;
    role: 'admin' | 'user' | 'viewer';  // Union type = limited choices
}

interface CreateUserResponse {
    id: number;
    name: string;
    email: string;
    role: string;
    createdAt: string;
}

test('POST /api/users — should create a new user', async ({ request }) => {
    const payload: CreateUserRequest = {
        name: 'Jane Smith',
        email: 'jane@example.com',
        role: 'admin'
        // role: 'superadmin'   // ❌ Compile error! Not in the union.
    };

    const response = await request.post('/api/users', { data: payload });
    expect(response.status()).toBe(201);

    const body: CreateUserResponse = await response.json();
    expect(body.name).toBe('Jane Smith');
    expect(body.role).toBe('admin');
    expect(body.id).toBeGreaterThan(0);
    expect(body.createdAt).toMatch(/^\d{4}-\d{2}-\d{2}T/); // ISO date
});
💡 SDET Pro Tip: Define all your API contracts as TypeScript interfaces. When the backend changes a field, your tests fail at compile time instead of silently passing with undefined values. This is a game-changer for API test maintenance.
